Piece 2: pollable AI task queue
Why: the connected AI (Scout) cannot receive inbound webhooks, so it polls for work. The member's request must land somewhere the AI can fetch with the member's bearer key.
Endpoints (all under the existing bearer-key auth; a key sees ONLY its own member's tasks):
POST /api/assistant/tasks — submit a task. Auth: member session. Body: { "prompt": "Add 'AI test' to the end of my bio" }. Returns { "id", "status": "pending", "created_at" }.
GET /api/assistant/tasks?status=pending — list tasks. Auth: bearer key. Returns the member's pending tasks, oldest first. Support ?status= filter (pending, claimed, done, failed).
PATCH /api/assistant/tasks/:id — update status. Auth: bearer key. Body: { "status": "claimed" | "done" | "failed", "note": "..." }. Only the key that claimed a task may move it to done/failed.
Rules:
Scope it: add tasks-read / tasks-write scopes (or document which existing scopes cover these); the key-creation UI must offer them.
Tasks expire after 24h (status → expired, excluded from pending).
Rate-limit the poll endpoint (generous — polling every 2–5 minutes is the expected pattern).
The existing draft/approval flow is unchanged: the AI reads via API, writes go through profile-draft/wishlist-draft scopes, drafts pause in the review UI, the member approves. The queue only carries the request, never executes it.
